# FLOWS.md — сценарии: кто что вызывает и в каком порядке

`CONTRACTS.md` описывает **форму** данных между модулями.
Этот файл описывает **последовательность действий**: что происходит, в
каком модуле, в какой транзакции и что будет при сбое.

## Как читать

- **[TX]** — начало транзакции БД. Всё до **[/TX]** коммитится или
  откатывается целиком.
- **ПОСЛЕ КОММИТА** — действие вне транзакции. Это всегда внешние системы
  (Redis, ML-сервис, WebSocket): они не умеют откатываться вместе с БД,
  поэтому не должны быть внутри.
- Модуль в **жирном** — чей код выполняет шаг.

## Общее правило по деньгам

Ни один модуль, кроме Rewards, не может создать `DiscountGrant`.
Ни одно обещание скидки не показывается пользователю до успешного
резерва. Порядок всегда: **резерв → обещание → потребление**.

## Сценарий 1. Регистрация клиента (с реферальным кодом)

**Триггер:** пользователь отправил форму регистрации.
**Участники:** Identity → Client → Rewards.

1. **Identity** создаёт `User` с `role=CLIENT`.
2. **Club** проверяет `ClubScope(club_id).is_active`. Клуб неактивен →
   400, дальше не идём.
3. **Client** валидирует `referral_code`, если он передан:
   находит владельца кода, проверяет `SelfReferralError`.
4. **[TX]**
   - **Client** создаёт `Client` с `user_id`, `club_id`, `display_name`,
     `membership`, собственным сгенерированным `referral_code`.
   - если код был валиден — `client.attach_referrer(referrer_id)`
   - **Rewards** (прямой вызов, если есть реферер):
     `ReserveBudgetCommand(source_type=REFERRAL, source_id=client_id, ...)`

     Резервируются **обе стороны сразу**: и скидка новичку, и будущая
     скидка пригласившему. Иначе сеть пообещает награду, которую не
     сможет выполнить.

     Клубы могут быть разными — тогда это две строки `BudgetReservation`
     в двух бюджетах. Блокировать бюджеты **строго в порядке возрастания
     `club_id`** — иначе две параллельные регистрации в зеркальных клубах
     дадут дедлок.
   - **Rewards** сразу потребляет долю новичка →
     `DiscountGrant(purpose=REFERRAL_INVITEE, applicable=MEMBERSHIP)`
5. **[/TX]**

**Если резерв не прошёл (`INSUFFICIENT_FUNDS`):** регистрация всё равно
успешна, `referred_by_client_id` сохраняется, но `DiscountGrant` не
создаётся и **интерфейс не показывает обещание реферальной скидки**.
Показать и не выполнить — хуже, чем не показать.

**Идемпотентность:** `idempotency_key` резерва = `f"referral:{client_id}"`.
Повторная отправка формы не создаёт вторую скидку.

## Сценарий 2. Проход через турникет — самый частый

**Триггер:** адаптер турникета прислал проход (в MVP — ручной вызов или
импорт). 15 запросов/сек в пике по сети.
**Участники:** Visit → Engagement (+ Redis).

1. **Visit** проверяет `external_id` на уникальность. Уже есть →
   возвращаем 200 и **ничего не делаем**. Это не ошибка: повторная
   загрузка выгрузки — штатная ситуация.
2. **[TX]**
   - **Visit** сохраняет `Visit`
   - **Visit** прямым вызовом передаёт `VisitRecorded` в **Engagement**
     (без Kafka — обоснование в `CONTRACTS.md`, раздел 4)
   - **Engagement**, один обработчик, три действия:
     1. `ClientChallenge.register_visit(required_visits)` — если вернул
        `True`, то `complete_stage()` и выдача
        `ClientAchievement` за этап
     2. пересчёт числа визитов клиента → проверка
        `AchievementDefinition` с `rule_type=VISITS_TOTAL`, выдача новых
        ачивок через `ClientAchievement.grant(source_key=...)`
     3. ранг **не пишется** — он вычисляется на чтении
3. **[/TX]**
4. **ПОСЛЕ КОММИТА** — **Engagement**:
   - `redis.zincrby(f"leaderboard:{club_id}:{iso_week}", 1, client_id)`
   - инвалидация кэша ранга: `redis.delete(f"rank:{client_id}")`
   - push в WebSocket тем, кто сейчас смотрит лидерборд клуба

**Почему Redis после коммита:** он не откатывается вместе с транзакцией.
Если сделать наоборот и транзакция упадёт, счётчик останется завышенным
навсегда. При сбое Redis лидерборд слегка разъедется — это чинится
пересчётом из `Visit`, а вот испорченный счётчик не чинится ничем.

**Идемпотентность:** обеспечивает Visit через `external_id`.
Engagement защиту не дублирует — если сюда пришёл дубль, это баг Visit.

## Сценарий 3. Подтверждение покупки управляющим

**Триггер:** управляющий нажал «подтвердить оплату». Это **симулятор
внешней кассы**, не платёжный шлюз — данных карты здесь нет.
**Участники:** Club → Rewards → Client → Rewards.

1. **Club** проверяет: актор имеет роль `CLUB_MANAGER` и
   `club.is_managed_by(actor.user_id)`, и клиент принадлежит этому клубу.
2. **Rewards** отдаёт `GetApplicableGrantsQuery(client_id, purchase_type)`
   → список применимых `DiscountGrant`.
3. **Client** считает итог: сумма скидок в пределах cap, `discount_amount`
   не больше `gross_amount`.
4. **[TX]**
   - **Client** создаёт `Purchase` (неизменяемый факт)
   - **Rewards** гасит применённые гранты: `grant.redeem(purchase_type)`
   - **Client** обновляет `client.apply_renewal(months)` — value object
     абонемента
5. **[/TX]** — все три либо есть, либо нет. Погашенная скидка без покупки
   и покупка без погашения одинаково недопустимы.

6. **Если это первая покупка абонемента и есть реферер** —
   **ПОСЛЕ КОММИТА**, **Client** публикует `FirstMembershipPurchased`:
   - **Rewards** потребляет долю пригласившего из резерва, созданного
     ещё в сценарии 1 → `DiscountGrant(purpose=REFERRAL_REFERRER,
     applicable=RENEWAL)`
   - `source_key = f"referral_referrer:{purchase_id}"`

**Почему награда пригласившему — только сейчас, а не при регистрации:**
иначе реферальную программу можно фармить регистрациями без покупок.
Деньги двигаются только на подтверждённом факте оплаты.

**Идемпотентность:** `Purchase.idempotency_key` от управляющего.
Повторное нажатие не создаёт вторую покупку и вторую награду.

## Сценарий 4. Обнаружение риска оттока (фоновый job)

**Триггер:** расписание, раз в сутки ночью.
**Участники:** Engagement → ML-сервис → Engagement.

Это ответ на открытый вопрос 3 из `CONTRACTS.md`: ML вызывает **фоновый
job**, не синхронный запрос. Причина — 48 000 клиентов нельзя скорить в
момент открытия панели, а свежесть в пределах суток здесь достаточна.

1. **Engagement** выбирает кандидатов: клиенты со статусом `ACTIVE`,
   у которых нет открытого `RetentionCase`, и есть хоть какая-то история
   визитов.
2. **Engagement** по каждому считает признаки из `Visit`:
   `days_since_last_visit`, `visits_last_30d`, `visits_prev_30d`,
   `median_interval_days`.
3. **Engagement** зовёт ML: `POST /api/v1/predict` с `task=churn`,
   `subject_id=client_id`, `features={...}`.
4. **Ответ ML:** `risk_score` и `contributions` → в `risk_reasons`
   человеческим текстом («11 дней без визита при обычных 4»).

   **ML недоступен или `is_fallback=true`** → правило-заглушка:
   `days_since_last_visit >= 11` даёт `risk_score=1.0`, иначе `0.0`.
   Панель продолжает работать, просто список хуже отсортирован.
5. **[TX]** **Engagement** создаёт `RetentionCase` для тех, у кого
   `risk_score` выше порога. UNIQUE на `(client_id, status=OPEN)`
   не даёт job'у наплодить дубли при повторном запуске. **[/TX]**

**Cap:** панель отдаёт максимум 20 карточек на страницу, сортировка
`risk_score DESC`. Без этого управляющий получит триста карточек и не
откроет ни одной — та же проблема, с которой пришёл заказчик.

## Сценарий 5. Решение управляющего по кейсу

**Триггер:** управляющий нажал «Предложить скидку» или «Отклонить».
**Участники:** Club → Engagement → Rewards → Engagement.

1. **Club** проверяет, что кейс принадлежит клубу этого управляющего.
2. **[TX]**
   - **Engagement**: `case.resolve(decision, decided_by_user_id, comment)`
   - `DISMISS` → статус `DISMISSED`, конец.
   - `OFFER_DISCOUNT` → статус **остаётся `OPEN`**
   - **Rewards**: `ReserveBudgetCommand(source_type=RETENTION,
     source_id=case_id, amount)` → сразу
     `ConsumeReservationCommand` → `DiscountGrant(purpose=RETENTION)`
   - только если Rewards вернул `GRANTED` → **Engagement**:
     `case.confirm_offer()` → статус `OFFER_CREATED`
3. **[/TX]**

**Если `INSUFFICIENT_FUNDS`:** кейс остаётся `OPEN`, управляющий видит
«фонд клуба на этот месяц исчерпан». Он не должен узнать об этом после
того, как клиенту уже показали скидку.

**Ключевое:** статус `OFFER_CREATED` ставится **после** ответа Rewards,
а не до. Это защита от обещания без денег, и она зашита в домен —
`confirm_offer()` вызывается отдельно от `resolve()`.

## Сценарий 6. Закрытие недели лидерборда

**Триггер:** расписание, понедельник 00:05.
**Участники:** Engagement (+ Redis).

1. **Engagement** по каждому клубу: `redis.zrevrange(f"leaderboard:{club_id}:{prev_week}", 0, N-1)`
2. **[TX]** выдача `ClientAchievement` каждому из топ-N,
   `source_key = f"leaderboard:{club_id}:{prev_week}:{client_id}"`
3. **[/TX]**
4. Ключ прошлой недели остаётся в Redis с TTL — история топов.

**Rewards в этом сценарии не участвует вообще.** Приз за топ недели —
ачивка, не деньги. Именно поэтому здесь нет ни резерва, ни бюджета, ни
транзакционной связи с финансовым модулем: денежной границы просто нет.

## Сценарий 7. Личный кабинет (чтение)

**Триггер:** клиент открыл страницу.
**Участники:** Client + Engagement + Rewards, параллельные запросы.

| Что показываем | Откуда |
|---|---|
| Профиль, абонемент, дата окончания | **Client** |
| Реферальный код и сколько друзей пришло | **Client** |
| Ранг и прогресс до следующего | **Engagement**, вычисляется из числа визитов + `RankTier`, кэш в Redis |
| Ачивки | **Engagement**, `ClientAchievement` |
| Прогресс онбординга | **Engagement**, `ClientChallenge` |
| Место в топе клуба | **Engagement**, Redis `ZREVRANK` |
| Доступные скидки | **Rewards**, `DiscountGrant` со статусом `AVAILABLE` |

Здесь видно, почему `ClientSnapshot` не отдаёт ранг: снапшот — это то,
что **модуль передаёт модулю**, а кабинет — это **экран**, который
собирается из трёх источников. Разные вещи.

## Сводка: где деньги, а где нет

| Сценарий | Rewards участвует | Транзакция с деньгами |
|---|---|---|
| 1. Регистрация с рефералом | да | резерв обеих сторон + грант новичку |
| 2. Проход турникета | **нет** | — |
| 3. Подтверждение покупки | да | погашение грантов + грант рефереру |
| 4. Обнаружение риска | **нет** | — |
| 5. Решение по кейсу | да | резерв + грант retention |
| 6. Закрытие лидерборда | **нет** | — |
| 7. Кабинет | чтение | — |

Три из семи сценариев не касаются денег вовсе — это прямое следствие
неденежного онбординга. Меньше денежных границ = меньше мест, где
можно порушить экономику под нагрузкой демо.
